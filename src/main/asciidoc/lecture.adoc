typedef struct {
    int year;
    int month;
    int day;
} Date;
/* "stack allocation" */
Date val_date =
  {.year = 2026, .month = 8, .day = 15};
/* "heap allocation" */
Date* ptr_date = malloc(sizeof(Date));

*ptr_date = val_date; // values copied
ptr_date->day++; // value on heap increased
print_date(val_date); // 2026-8-15
print_date(*ptr_date); // 2026-8-16

Date modify_months(Date date1, Date *date2) {
  date1.month++;
  date2->month++;
  return date1;
}

Date result =
  modify_months(
    *ptr_date, // value at pointer
    &val_date  // address of value
);

// passed by pointer, modified
print_date(val_date); // 2026-9-15
//  passed by value, unmodified
print_date(*ptr_date); // 2026-8-16
// new value
print_date(result); //2026-9-16

void fillInterval(Date* from, Date* to) {
  *from = (Date){.year = 2026,
    .month = 8, .day = 15};
  Date dateTo = (Date){.year = 2026,
    .month = 8, .day = 16};
  to = &dateTo;
  free(from);
}

void main() {
  Date* from = malloc(sizeof(Date));
  Date* to = NULL;
  fillInterval(from, to);
  print_date(*from); //Access violation

@AllArgsConstructor @ToString
class Date {
  int day; int month; int year; }

int modifyMonths(int month, Date date) {
  month++; date.month++;
  return month; }

Date d = new Date(15, 8, 2026);
int month = 8;
int result = modifyMonths(month, d);
println(month);  // 8
println(d);      // Date(d=15, m=9, y=2026)
println(result); // 9

== So, these design decisions from 1995 were justified

[cols="50a,50a"]
|===
|
* No allocations on stack
* No manual deallocation
|  => no dangling references
|
* Garbage collection
|=> no "lost reference" problem
|
* 8 predefined primitive types (`byte`, `short`, `int`, `long`, `char`, `float`, `double`, `boolean`)
| A performance trade-off, which complicated the type system, language teaching and led to further problematic decisions such as need of boxing to use these types in generics.
|===

== Here comes Valhalla!

* *Value objects* — identity-free instances of immutable classes, which _may_ be allocated on stack, passed by value, and distinguished only by its own internal state.
* You may think of `value` types as new primitives: immutable entities distinguished _only_ by their internal state.

[source,java]
----
public final value class LocalDate implements ... {
    private final transient int year;
    private final transient byte month;
    private final transient byte day;
    ... }
----

//== `value` type is like a `struct`, but not a `struct`

//* You can declare an immutable class or record to be `value`.
//* Unlike C, C# and Rust `struct`, value types allow self-reference:

//[source,java]
//----
//value record Employee(
//        String name,
//        int salary,
//        Employee manager //compiles!
//) {}
//----

//* JVM will decide the implementation details

== Conclusions about Linked List

* A "mini-heap" based implementation beats classic `LinkedList` nearly everywhere, while keeping the big-O promises and having *3x less memory overhead*.
* Only became possible with Valhalla.

== Conclusions

* This was the only one example. Valhalla opens the gate for a huge number of optimizations in the standard library. The "mini heap" idea may be fruitful in many fields.
* Valhalla comes "the Java way": without making the user think about low-level details, it unlocks automatic optimizations.
* Users should expect a significant performance boost with the newer versions of Java.
