A long time ago in a galaxy far, far away…​

  • Java celebrated 30th anniversary in 2026, and Valhalla preview release is planned for March 2027.

  • The story starts 54 years ago: with features and dangers of low-level languages like C, for which Java took its own approach.

In C, we have full control of where we allocate things

typedef struct {
    int year;
    int month;
    int day;
} Date;
/* "stack allocation" */
Date val_date =
  {.year = 2026, .month = 8, .day = 15};
/* "heap allocation" */
Date* ptr_date = malloc(sizeof(Date));

*ptr_date = val_date; // values copied
ptr_date->day++; // value on heap increased
print_date(val_date); // 2026-8-15
print_date(*ptr_date); // 2026-8-16

In C, we have full control of how we pass the arguments

Date modify_months(Date date1, Date *date2) {
  date1.month++;
  date2->month++;
  return date1;
}

Date result =
  modify_months(
    *ptr_date, // value at pointer
    &val_date  // address of value
);

print_date(val_date); // 2026-9-15
print_date(*ptr_date); // 2026-8-16
print_date(result); //2026-9-16

C language horrors: dangling pointers

void fillInterval(Date* from, Date* to) {
  *from = (Date){.year = 2026,
    .month = 8, .day = 15};
  Date dateTo = (Date){.year = 2026,
    .month = 8, .day = 16};
  to = &dateTo;
  free(from);
}

void main() {
  Date* from = malloc(sizeof(Date));
  Date* to = NULL;
  fillInterval(from, to);
  print_date(*from); //Access violation
  print_date(*to);
}

Java to the rescue: no *, no &, everything is predefined

@AllArgsConstructor @ToString
class Date {
  int day; int month; int year; }

int modifyMonths(int month, Date date) {
  month++; date.month++;
  return month; }

Date d = new Date(15, 8, 2026);
int month = 8;
int result = modifyMonths(month, d);
println(month);  // 8
println(d);      // Date(d=15, m=9, y=2026)
println(result); // 9

Java arrays of objects contain references

Date[] dates = new Date[3];

dates[0] = new Date(1, 1, 2023);
dates[1] = new Date(2, 2, 2024);
dates[2] = dates[1];

Lost reference is not a problem

dates = new Date[0];

So, these design decisions from 1995 were justified

  • No allocations on stack

  • No manual deallocation

⇒ no dangling references

  • Garbage collection

⇒ no "lost reference" problem

  • 8 predefined primitive types (byte, short, int, long, char, float, double, boolean)

A performance trade-off, which complicated the type system, language teaching and led to further problematic decisions such as need of boxing to use these types in generics.

Of course, Java way is not the only way…​

C# ("Java competitor", 4 years younger than Java)

  • has GC, but also has struct for "stack-allocated" value types and ref for passing values by reference.

  • ref escape scope is checked by the compiler: you cannot pass a ref to something stack-allocated into a global storage.

  • List<int> doesn’t use boxing.

Rust ("C competitor", roughly 10 years younger than Java)

  • Has struct, immutable (&) and mutable (&mut) references

  • Borrow checking/lifetime checking in compile time.

…​But for the 20 years that followed, C and Java have remained the top 2 languages on TIOBE index

LinkedList problems

  1. Node is 24 bytes per element (while ArrayList typically takes only 4 bytes per compressed object reference)

  2. Potentially poor data locality — less effective CPU cache usage

  3. Higher load on GC

LinkedList$Node doesn’t need to be that large…​

  • XOR linked list: instead of storing prev and next, it’s sufficient to store prev XOR next in one field.

  • During all the list traversals, one either knows current prev or current next and can retrieve the unknown using the XOR operation.

  • Java does not allow this trick, as "pointers" are hidden.

Here comes Valhalla!

  • Value objects — identity-free instances of immutable classes, which may be allocated on stack, passed by value, and distinguished only by its own internal state.

  • You may think of value types as new primitives: immutable entities distinguished only by their internal state.

public final value class LocalDate implements ... {
    private final transient int year;
    private final transient byte month;
    private final transient byte day;
    ... }

Flattened arrays

LocalDate[] dates =
  (LocalDate[]) ValueClass
  .newNullRestrictedNonAtomicArray(
    LocalDate.class, 3,
    LocalDate.now());

boolean isFlat =
  ValueClass.isFlatArray(dates); //true

  • LocalDate[100_000] before Valhalla: (24 LocalDate object + 4 ref) * 100 000 = 2 800 000 bytes, 100 000 allocations.

  • Flattened LocalDate[100_000]: (8 flattened LocalDate) *100 000 = 800 000 bytes, zero allocations.

LinkedList revamped: the idea of "mini-heap"

  • value record Node(int prevXorNext, Object ref)

  • flattened array with the list itself + the chain of "holes"

  • exponentially grow the array as needed

  • all the O(1) promises kept

  • 8 bytes per Node (4 for int + 4 for the compressed ref) — 3x gain vs LinkedList$Node!

Conclusions about Linked List

  • A "mini-heap" based implementation beats classic LinkedList nearly everywhere, while keeping the big-O promises and having 3x less memory overhead.

  • Only became possible with Valhalla.

Conclusions

  • This was the only one example. Valhalla opens the gate for a huge number of optimizations in the standard library. The "mini heap" idea may be fruitful in many fields.

  • Valhalla comes "the Java way": without making the user think about low-level details, it unlocks automatic optimizations.

  • Users should expect a significant performance boost with the newer versions of Java.
